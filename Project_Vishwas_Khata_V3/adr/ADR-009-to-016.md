# Project Vishwas Khata — V2 architecture decisions (owner approval pending)

> Every ADR is PROPOSED, not implemented. This annex augments, not supersedes, `ADR-001-to-008.md`. Owner: project proposer. Date: 2026-10-27.

## ADR-009 — Business-day UTC boundary from IANA timezone
**Context:** SQL `date(UTC string)` misclassifies early-morning Indian sales. **Decision:** API uses date + merchant IANA zone `Asia/Kolkata`; computes UTC start inclusive/end exclusive. **Alternatives:** store naive local time; rejected (ambiguous/audit-unfriendly). **Consequences:** shared time helper; test at 00:30 IST. **Evidence gate:** T-037/T-045. **Revisit:** multi-timezone rollout.

## ADR-010 — Financial journal defense in depth
**Context:** application-only balance checks can be bypassed by bugs/concurrent requests. **Decision:** domain transaction guard plus `002_integrity_hardening.sql` immutability, same-customer reversal-sign check and no-negative balance. **Alternatives:** mutable balance field; rejected for auditability. **Consequences:** certain reversal sequences must be staged carefully. **Evidence gate:** reference tests and actual API concurrency suite. **Revisit:** production PG conversion.

## ADR-011 — Recordkeeping completeness, not credit decisioning
**Context:** original idea describes "loan readiness". **Decision:** report only count/recency/completeness of records and explicitly refuse inference of credit eligibility, rates, approval or compliance status. **Alternatives:** heuristic loan score; rejected without lender contract/data. **Evidence:** T-019, T-042. **Revisit:** actual regulated partner/lender-led design.

## ADR-012 — Observations separate from settlement
**Context:** daily brief could invent merchant revenue from credit transactions. **Decision:** store `sales_events`, `visit_events` only from explicit/synthetic observations and label quality/completeness. **Alternatives:** deduce sales from khata, Paytm soundbox; rejected without evidence. **Evidence:** T-010/T-032/T-037. **Revisit:** authorized settlement adapter.

## ADR-013 — No public demo auth
**Context:** hosted hardcoded merchant creates trivial access flaw. **Decision:** demo bypass exclusively loopback; hosted code needs real auth/HTTPS/permissions, even for demo writes. **Alternative:** public synthetic writable site; rejected due to attack/trust. **Evidence:** T-016/T-034. **Revisit:** approved public read-only showcase.

## ADR-014 — Vendor integration verified at build time
**Context:** ASR and TTS models/SDKs and limits change. **Decision:** configurable provider ports; freeze model only after current official docs + live synthetic probe, log chosen version. **Alternative:** hardcode Hyderabad model names; rejected as stale. **Evidence:** provider compatibility report. **Revisit:** each vendor model/version migration.

## ADR-015 — Human-controlled customer follow-up
**Context:** suggestions could accidentally become consentless messaging. **Decision:** view, dismiss, mark manually done; no outbound contact or marketing automation. **Alternative:** auto-send discount WhatsApp; deferred. **Evidence:** no network send tests. **Revisit:** pilot consent and verified customer communication need.

## ADR-016 — Merchant-first Track 1 and future consumer surface
**Context:** original Vishwas combined two fintech products under one platform. **Decision:** build Khata only. Shared infrastructure remains an architectural direction; Vishwas Pay, fraud detection, deepfake prevention and graph AML are independently evaluated future products. **Alternative:** full two-surface MVP; rejected as unrealistic solo hackathon scope. **Evidence:** demo scope + deck review. **Revisit:** after real merchant MVP and separate consumer dataset/permissions.
