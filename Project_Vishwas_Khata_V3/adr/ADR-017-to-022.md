# Version 3 Design Decisions — Proposed, not production-approved

**Owner:** Project proposer. **Date:** 2026-10-27. All decisions are subject to implementation and verification. These supplement ADR-001–016. They override conflicting prior examples, never retroactively turn the proposal into working software.

## ADR-017 — Database independently binds approved drafts to posted money
- **Context:** V2 database triggers validated nonnegative receivables and immutable entries but could still accept a signed entry with a different amount than its referenced draft.
- **Decision:** V3 migration requires same merchant, customer, entry type, exact amount, approved state and simulated provenance. Draft confirmation requires an existing matching row. Confirmed draft rows become immutable.
- **Rejected alternative:** trust API handler alone; does not withstand internal bugs or direct SQL writes.
- **Consequence:** insert journal before state transition in one transaction. Data migration must diagnose historic mismatches before upgrading.
- **Evidence:** `tests/test_v3_invariants.py`; actual server integration remains NOT RUN.

## ADR-018 — Append-only observed activity with compensating voids
- **Context:** V2 allowed editing/deleting a manually recorded sale or visit and consequently rewriting reported facts without an audit trail.
- **Decision:** immutable event and distinct merchant-owned correction/void records; query nonvoid observations only, retain history.
- **Rejected alternative:** soft overwrite fields without revision evidence.
- **Consequence:** two new API paths, a third migration, an explicit operator correction workflow. Separate production retention handling remains TBD.
- **Evidence:** V3 source/void reference tests, application tests NOT RUN.

## ADR-019 — Idempotent merchant observation writes
- **Context:** voice/mobile clients retry network requests, potentially inflating event counts.
- **Decision:** `client_operation_id` per merchant/source collection, stable replay for identical canonical payload, 409 if divergent, exact uniqueness in SQLite.
- **Rejected alternative:** optimistic assumption users only tap once.
- **Consequence:** browser must persist pending operation ID until resolved; no new key on uncertain network outcome.
- **Evidence:** reference oracle and negative tests; real HTTP concurrency NOT RUN.

## ADR-020 — Observations cannot certify complete revenue or absence of visits
- **Context:** a few manual entries cannot establish full sales or factual churn.
- **Decision:** expose `NO_DATA` vs `PARTIAL_UNVERIFIED`; prohibit `COMPLETE_VERIFIED` in MVP. Label inactivity as absence of *recorded* visits, with minimum history and source IDs.
- **Rejected alternative:** equate no event with zero revenue or no customer arrival.
- **Consequence:** business deck must use qualified language; V2 `cash_sales_paise` name replaced before API deployment; V3 contract uses `observed_sales_paise`.
- **Evidence:** `reference/observations_reference.py`, application copy tests pending.

## ADR-021 — Vendor-edge adapter, no provider-specific API leakage
- **Context:** Sarvam's provider endpoint expects a multipart field `file`; Vishwas client API expects `audio`. A bad pass-through integration would fail, and model defaults evolve.
- **Decision:** server adapter maps endpoint, field, authentication, model/language, size limits and error states. Keep all key material server-side. No journal writes in provider code.
- **Rejected alternative:** embed vendor SDK/API key in browser or assume historical model ID never changes.
- **Consequence:** current official docs and live synthetic probe mandatory before P1 is advertised as implemented.
- **Evidence:** docs-based contract reviewed; authenticated provider call NOT RUN.

## ADR-022 — Controlled revision and evidence labeling
- **Context:** lengthy architectural proposals can be mistaken for implemented/verified code.
- **Decision:** keep docs-as-code; source design claims have explicit source/assumption/test status. Audit should prove invariants via executable tests and verify OpenAPI contract structure, not count words.
- **Rejected alternative:** use number of headings as completion certification.
- **Consequence:** V3 audit report separately identifies prior substantive gaps, implementation blockers and conditions for build readiness.
- **Evidence:** `verification/verify_v3.py`, `verification/V2_TO_V3_AUDIT.md`.
