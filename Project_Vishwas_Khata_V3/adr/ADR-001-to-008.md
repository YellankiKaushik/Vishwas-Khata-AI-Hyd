# Project Vishwas Khata — Architecture Decision Record Register

> Decision state: **Proposed; project owner review pending**. These are not retrospective descriptions of implemented software. Future replacements must reference superseded ADR IDs and contain a data/contract migration plan.

## ADR-001 — Merchant-first product and single demo journey

**Context:** The Hyderabad concept combined consumer scam interception, merchant credit recording, narration, advanced graph detection, loan readiness and autonomous agents. Bengaluru Track 1 asks for an AI business partner for merchants. A one-day solo prototype cannot credibly validate every frontier.

**Drivers:** Clear user, buildability, technical trust, judging relevance, limited time and data access.

**Options:** (A) Keep both products; (B) build only Vishwas Pay; (C) build Vishwas Khata and document Pay as future. **Decision:** C.

**Consequences:** Strong closed merchant loop; consumer trust ideas remain in research archive; no claim of a functioning fraud model. **Revisit:** Merchant MVP works, user studies support extension, and payment/fraud data contracts become available.

## ADR-002 — Exact, append-only receivable journal with explicit user approval

**Context:** Speech and model extraction can be wrong; a misheard ₹500/₹5,000 could materially alter customer debt.

**Options:** Direct model-to-ledger write; mutable CRUD record; draft-confirm-append-only journal. **Decision:** Draft-confirm-append-only, integer paise, atomic DB commit, compensating reversals, duplicate-safe IDs.

**Invariant:** A credit increases the receivable; repayment decreases it; no unconfirmed mutation and no silent deletion. **Consequence:** More UI clicks, but necessary auditability. **Revisit:** Never relax based only on confidence score; only after separately validated authorization/accounting architecture.

## ADR-003 — Modular monolith and SQLite local MVP

**Context:** A new system without proven traffic needs quick, reproducible prototyping.

**Options:** Microservices and Kafka; serverless functions with several managed data services; modular FastAPI app + local SQLite. **Decision:** Last option, with separate domain and vendor ports.

**Consequences:** Easy transactions and setup; SQLite writer concurrency constrained; local demo identity unsuitable for public use. **Revisit:** Real authenticated multi-tenant pilot or measured concurrency limits; migrate to PostgreSQL first.

## ADR-004 — Fact-anchored merchant insights and deterministic fallback narration

**Context:** Unbounded LLM advice can fabricate revenue, loan eligibility and customer churn. 

**Options:** Let model derive metrics; scripted static demo; deterministic metrics with optional bounded LLM phrasing. **Decision:** Third option. Numeric facts derive from posted journal and explicit sales/visits with provenance. Model cannot invent financial values.

**Consequence:** Less open-ended creativity; more trustworthy demo. **Revisit:** After model grounding benchmark and user value tests; still preserve authoritative facts.

## ADR-005 — Speech provider adapter, not vendor lock-in throughout application

**Context:** Sarvam supports Indian-language speech APIs, but exact model aliases, SDK signatures, quotas and cost may change. Vendor failure should not erase ledger capability.

**Options:** Direct model call in browser; provider SDK embedded in each handler; server-side adapter with fake and typed fallback. **Decision:** Third option.

**Consequences:** Adapter contract must be maintained; simulated fixture clearly labeled. **Revisit:** New provider or real cost/latency data justifies multi-vendor arbitration.

## ADR-006 — Synthetic-only MVP with no Paytm private integrations

**Context:** Original diagrams refer to Paytm-facing consumer risk signals and merchant data but no authorized integration exists in supplied sources. Merchant credit is not verified settlement.

**Options:** Fake Paytm integration UI; request real customer/payment data immediately; independent synthetic merchant experience. **Decision:** Independent synthetic MVP.

**Consequence:** Cannot claim real payment fraud intervention or production readiness. **Revisit:** Authorized Paytm partnership, complete API docs, purpose/privacy agreement and integration test.

## ADR-007 — Merchant-authorized suggestions, never auto-messaging

**Context:** A rule could detect an absence in **recorded** visit events; it does not establish true customer churn nor permission to contact the person.

**Options:** Auto-send message; generate draft suggestion reviewed by merchant; suppress all actions. **Decision:** Merchant-reviewed draft, no external send capability.

**Consequence:** Measurable action intent without unauthorized outreach. **Revisit:** Permissioned channel, messaging consent, opt-out implementation and evaluation evidence.

## ADR-008 — Experimental revenue assumptions and benchmark honesty

**Context:** No live merchant pilot, conversion rates, pricing interviews or vendor invoice samples supplied.

**Options:** Claim huge savings/TAM; omit business model; transparent subscription hypotheses with cost formulas and explicit validation plan. **Decision:** Third option.

**Consequences:** Early business slide may contain unknown values; better credibility. **Revisit:** Observed pricing, CAC, cohort activity, ASR/TTS charges, merchant interviews and demonstrated merchant outcomes.
